更新与资料核对日期：2026 年 10 月 20 日。

## 基础概念与性能指标

### 推理执行与推理能力

推理执行（inference）指使用训练好的模型生成结果；推理能力（reasoning）指模型解决数学、代码、规划等问题的能力。DeepInfer、vLLM、FlashMLA 主要涉及前者。DeepSeek-R1 的强化学习和蒸馏主要涉及后者。更长的思考过程会增加生成量，因此 reasoning 的发展也提高了对高效 inference 的需求。[^deepinfer][^r1]

Token 是模型处理文本的基本单位，可能是一个词、子词、汉字或其他片段。本文统一称为词元，讨论代码接口或性能单位时保留 `token`。

### 一次请求的两个阶段

| 阶段 | 执行内容 | 常见性能特征 | 用户感受 |
| --- | --- | --- | --- |
| 预填充（Prefill） | 处理已知输入，生成后续解码需要的状态 | 长输入形成较大的矩阵运算，通常更容易受计算能力限制 | 等待多久才开始回答 |
| 解码（Decode） | 根据已有前缀，逐步生成新词元 | 存在串行依赖；小批量时常受权重与缓存的读取带宽限制 | 回答时输出是否流畅 |

上述特征不是固定分类。批量大小、上下文长度、模型稀疏性、算子实现和通信方式都会改变瓶颈。判断系统性能时，应分别考虑计算、显存读写、设备间通信和 CPU 调度开销。[^distserve][^scaling-inference][^horace-brrr]

| 指标 | 含义 | 阅读实验时的用途 |
| --- | --- | --- |
| TTFT，Time to First Token | 从请求到达至返回首个词元的时间 | 检查排队、缓存命中和预填充成本 |
| ITL，Inter-Token Latency | 相邻输出词元的时间间隔 | 检查流式输出是否出现停顿 |
| TPOT，Time per Output Token | 输出阶段平均每词元耗时，具体定义依基准而定 | 比较解码速度 |
| Throughput | 系统单位时间完成的请求或词元数量 | 衡量总体处理能力 |
| Goodput | 满足延迟等服务约束的有效处理量 | 避免只追求吞吐而牺牲交互体验 |

首词元是否计入输出阶段、缓存命中的输入词元是否计入吞吐，都需要查看测量定义。较大的批量通常能提高权重复用和吞吐，也可能增加单请求等待时间。[^distserve][^scaling-inference]

### KV 缓存及其大小

因果注意力中，已处理词元的键和值（Key、Value）可以保存为 KV 缓存（KV cache），后续解码直接复用。这样避免重复计算历史前缀，但缓存会随请求数和上下文长度增长。[^scaling-inference]

对普通多头注意力或分组查询注意力，忽略分页对齐、元数据、不同层配置和额外缓存后，可作如下估算：

$$
M_{\mathrm{KV}} \approx 2BLTH_{\mathrm{KV}}ds.
$$

其中，$B$ 是批量中的请求数，$L$ 是层数，$T$ 是每个请求的已缓存词元数，$H_{\mathrm{KV}}$ 是 KV 头数，$d$ 是每头维度，$s$ 是每个元素的字节数；系数 $2$ 对应 K 和 V。不同请求长度不同时，应对各请求的 $T$ 分别求和。MLA、跨层共享和混合注意力需要按各自结构重新计数。

取单请求、32 层、8192 个词元、32 个 KV 头、每头 128 维、16 位缓存：

$$
M_{\mathrm{KV}}
=2\times1\times32\times8192\times32\times128\times2
=4{,}294{,}967{,}296\ \mathrm{bytes}
=4\ \mathrm{GiB}.
$$

同样条件下，KV 头数降为 8，缓存为 1 GiB。这个例子只计算 KV，不包含模型权重、临时张量和框架开销。它说明减少 KV 的存储维度，会同时影响可容纳请求数和解码读写成本。[^gqa]

### 常见并行方式

| 缩写 | 中文与英文 | 拆分对象及主要代价 |
| --- | --- | --- |
| TP | 张量并行，Tensor Parallelism | 拆分矩阵或层内计算，需要组合各设备的部分结果 |
| PP | 流水线并行，Pipeline Parallelism | 按层或阶段拆分模型，需要管理流水线空闲和阶段间传输 |
| EP | 专家并行，Expert Parallelism | 将不同专家放到不同设备，需要分发词元并合并专家输出 |
| DP | 数据并行，Data Parallelism | 多个执行副本处理不同请求，需要请求级负载均衡 |
| CP | 上下文并行，Context Parallelism | 拆分长序列处理，需要交换相关状态并平衡序列计算 |

这些方式可以组合，训练和推理中的具体实现也不同。Megatron-LM 是理解张量并行的重要起点；DeepSeek 的推理系统说明展示了注意力与专家部分采用不同并行策略的实例。[^megatron][^infra-overview]

### 从 MHA、MQA、GQA 到 MLA

多头注意力（Multi-Head Attention，MHA）中，不同头保存各自的 K、V。多查询注意力（Multi-Query Attention，MQA）让查询头共享一组 K、V，降低解码缓存和读取需求；分组查询注意力（Grouped-Query Attention，GQA）采用多组 KV，在共享程度和表达能力之间折中。[^mqa][^gqa]

DeepSeek-V2 的多头潜在注意力（Multi-head Latent Attention，MLA）把 K、V 信息压缩到较低维的潜在表示中，并通过变换合并避免在解码时完整展开高维历史状态。旋转位置编码（Rotary Position Embedding，RoPE）需要单独处理，以保留这种变换重组的可行性。[^v2]

| 方法 | 缓存设计 | 学习时应抓住的区别 |
| --- | --- | --- |
| MHA | 每头独立 K、V | 作为存储量和计算过程的基线 |
| MQA | 所有查询头共享一组 K、V | 通过共享减少 KV 头数 |
| GQA | 每组查询头共享 K、V | 通过分组控制共享程度 |
| MLA | 缓存压缩后的潜在表示及必要的位置信息 | 从表示维度减少缓存，配合计算变换 |

这些改变属于模型结构设计，需要相应训练或适配。MLA 与 FlashMLA 的职责不同：前者规定模型如何表示与使用信息，后者实现相应的高性能注意力算子。[^v2][^flashmla]

### FlashAttention：减少中间结果的显存读写

普通注意力容易将注意力分数矩阵和 softmax 结果写入显存，再读回来继续计算。FlashAttention 通过分块、在线 softmax 和输出累积，在片上存储中处理小块，减少中间张量在高带宽显存（High Bandwidth Memory，HBM）中的读写。[^flashattention]

FlashAttention 计算完整注意力，在通常浮点误差范围内保持相同数学运算；其主要改进是数据流和中间存储，完整注意力的计算量仍随序列长度呈二次增长。学习时需要区分减少 I/O、减少存储量与减少算法运算量。[^flashattention]

后续版本根据硬件继续调整线程分工和执行流水线。FlashAttention-3 利用 Hopper 的异步能力和低精度计算；FlashAttention-4 面向 Blackwell，讨论 Tensor Core 吞吐增长快于指数运算等资源时的新瓶颈。关注推理的读者可先学习前向计算，反向传播优化属于训练范围。[^flashattention3][^flashattention4]

### 连续批处理、分页与前缀复用

固定请求集合的批次中，短请求完成后可能留下无法立即利用的执行位置。Orca 的迭代级调度在生成轮次之间调整批次，让完成的请求退出、新请求加入。这是连续批处理的重要代表。[^orca]

PagedAttention 借鉴操作系统的分页思想，将逻辑连续的 KV 序列映射到按需分配的物理缓存块，减少碎片和过度预留，并支持块共享。vLLM 将这种机制用于服务系统，使有限显存能够容纳更多请求。[^pagedattention]

前缀缓存复用针对相同模型与兼容执行条件下的相同词元前缀，复用已经计算好的状态。SGLang 的 RadixAttention 用树结构管理共享前缀，适合公共提示词、多轮对话和分支生成。KV 前缀复用与基于语义相似度返回旧答案的“语义缓存”是不同机制。[^sglang-paper][^sglang-blog]

| 技术 | 主要减少的开销 | 不能由此推出的结论 |
| --- | --- | --- |
| 连续批处理 | 批次空位和调度等待 | 更大吞吐不等于每个请求延迟更低 |
| 分页 KV 缓存 | 碎片、预留与重复存储 | 不会消除上下文本身需要的缓存 |
| 前缀复用 | 已有前缀的重复计算 | 相似文本不能直接按精确前缀共享处理 |

### 量化：缩小表示与适配计算硬件

量化可以作用于权重、激活或 KV 缓存，分别改变模型存储、算子输入输出和历史状态的精度。低比特表示减少容量与传输需求，有配套算子时也能使用低精度计算能力。转换、缩放、解量化和内核布局的开销决定了实际收益。[^gptq][^awq][^deepgemm]

GPTQ 利用近似二阶信息，在逐步量化权重时补偿误差；AWQ 利用激活信息识别重要权重，通过缩放降低低比特表示误差。两者是学习训练后权重量化的代表材料。[^gptq][^awq]

“4-bit 模型”不能直接解释为全部运行张量都使用 4 位。阅读部署结果时，应区分权重、激活、累加和缓存的格式，并同时检查精度与速度。

### 投机解码与多词元预测

投机解码（Speculative Decoding）让较便宜的草稿模型提出多个候选词元，再由目标模型并行验证。连续通过的候选可以一起接受，失败位置按相应规则修正，然后进入下一轮。经典算法通过接受概率和残差分布修正，可保持目标模型的采样分布。分布保持不意味着固定随机种子下的文本轨迹必然逐字相同。[^specdec]

草稿速度、接受率、验证长度和系统负载共同影响收益。更长的草稿若大量被拒绝，会浪费计算和批处理容量。

| 工作 | 主要思路 | 与其他工作的关系 |
| --- | --- | --- |
| 经典投机解码 | 小模型起草，大模型验证 | 建立加速与分布保持的基础框架[^specdec] |
| Medusa | 多个预测头构造候选，再用树状机制验证 | 探索轻量草稿结构；不同训练和接受方案的保证需分别看[^medusa] |
| 多词元预测，Multi-token Prediction（MTP） | 训练时预测多个未来位置 | 可改善训练监督，也可提供投机解码能力[^mtp] |
| DeepSeek-V3 的 MTP | 将多词元预测纳入模型设计 | 需要区分训练目标与部署时使用方式[^v3] |
| DSpark | 半自回归草稿与按置信度安排验证长度 | 同时考虑草稿质量和引擎验证容量[^dspark] |
| DFlash / DFlash 2 | 并行块草稿；后续加入候选选择与局部依赖建模 | 为并行草稿提供另一种改进路径[^dflash][^dflash2] |

DSpark 用并行主体加轻量顺序模块改善草稿中的词元依赖，再根据前缀存活概率和引擎吞吐特征决定每个请求的验证长度。作者在 DeepSeek-V4 线上流量中报告，相对 MTP-1 基线，在匹配吞吐量的条件下，单用户生成速度提升 60%—85%；该数据对应作者的生产设置。DeepSpec 提供相关草稿训练与评估代码。[^dspark][^deepspec]

### 预填充分块与阶段分离

长输入的预填充会干扰正在逐步生成的请求。Sarathi-Serve 用分块预填充（Chunked Prefill）和调度策略，将长输入拆成小块，与解码任务安排到多个执行轮次中。过小的块也会增加调度和重复读取历史状态的开销，需要按负载调整。[^sarathi]

DistServe 将预填充与解码分配到不同 GPU 资源池，分别选择资源规模和并行策略。阶段分离需要传输 KV 状态，因此网络、缓存大小和请求分布都会影响收益。它优化的是同时满足 TTFT 和 TPOT 约束的有效吞吐。[^distserve]

### MoE：稀疏计算需要通信与负载均衡配合

混合专家模型（Mixture of Experts，MoE）用路由器为每个词元选择少量前馈子网络。稀疏 MoE 的重要先行工作早于 DeepSeek；“专家”是子网络的名称，其分工不必对应人类定义的学科。[^moe-2017]

DeepSeekMoE 的两项代表设计是细粒度专家与共享专家：前者允许更灵活的专家组合，后者承载公共知识，减少路由专家之间的冗余。[^deepseek-moe]

较低的每词元激活参数量不等于只需保存同等规模的模型权重。专家分布在多卡后，还会出现 token 分发、结果合并、不同专家忙闲不均等问题。DeepEP、EPLB、DeepGEMM 分别从通信、放置与复制、矩阵计算方面将稀疏计算兑现为运行收益。[^deepep][^eplb][^deepgemm]

### 稀疏注意力、跨层共享与混合状态

稀疏注意力通过选择部分历史信息，减少主要注意力计算；索引、打分与 Top-K 选择本身仍有成本，不能只计算被选中位置上的开销。

| 工作 | 原理与适用位置 |
| --- | --- |
| NSA，2025 | 结合粗粒度压缩、细粒度选择和局部处理，设计时兼顾端到端训练与硬件执行效率[^nsa] |
| V3.2 的 DSA，2025 | 用轻量索引器选择重要历史位置，再执行主要注意力计算；与 NSA 分别理解[^v32] |
| V4，2026 | 结合压缩稀疏注意力（CSA）和更强压缩的注意力（HCA），降低超长上下文成本[^v4] |
| V4.1，2026 | CSA2 跨层复用 KV、索引器状态和部分索引结果，结合 CED、低精度缓存及有限重放[^v41] |

跨层 KV 共享进一步减少需要独立保存状态的层数。共享层仍可拥有自己的查询投影，但复用其他层的 K/V。它改变模型结构和表示能力，需要与模型训练一起考虑。YOCO 是理解跨层共享与预填充省算思路的相关前序工作。[^kv-sharing-code][^yoco]

滑动窗口注意力（Sliding-Window Attention，SWA）和状态空间模型又引入不同的复用条件：窗口方法需要复用边界前的有效窗口；递推模型可能需要边界处的状态快照。混合模型因此需要比普通全注意力更复杂的缓存管理。Mamba 可作为高效递推序列模型的补充阅读，Unified Radix Cache 则提供混合状态服务系统的实例。[^mamba][^unified-radix]

## DeepSeek 开源生态与 DeepInfer

### 模型结构、算子和引擎的关系

DeepSeek 推理工作的主要学习价值在于模型与系统的共同设计：MLA 减少缓存，MoE 减少每词元参与的计算，低精度缩小存储和传输，算子库负责高效执行，通信与调度再把这些能力组合起来。每一层的优化都会改变下一层的瓶颈。[^v2][^v3][^insights]

| 层次 | 代表对象 | 负责的问题 |
| --- | --- | --- |
| 模型结构 | MLA、DeepSeekMoE、DSA、CSA2、CED、MTP/DSpark | 定义计算图、状态表示与草稿机制 |
| 计算算子 | FlashMLA、DeepGEMM、DeepSelect、TileKernels | 优化注意力、矩阵乘法、选择和融合操作 |
| 通信与放置 | DeepEP、EPLB | 传输词元与专家结果，减少设备间负载不均 |
| 引擎运行 | DeepInfer | 执行模型、组织并行、安排批次、验证草稿与采样 |
| 服务与存储 | 请求路由、KV 缓存系统、阶段分离、3FS 等 | 管理多请求、多副本和分层状态；部分需要外部系统完成 |

这张表是职责划分，不表示全部项目都以独立组件的形式直接包含在当前 DeepInfer 开源版本中。特别是 3FS，属于可支撑训练和推理的数据基础设施。[^deepinfer][^three-fs]

### 从开源组件到引擎

2025 年 2 月的开源周集中公开了 FlashMLA、DeepEP、DeepGEMM、并行与负载均衡相关代码、3FS 和 smallpond，并发布 V3/R1 推理系统说明。[^infra-index]

2025 年 4 月的官方说明解释：内部引擎源于较早的 vLLM 分支，已经出现较大代码分化，还依赖内部集群基础设施；当时优先采用拆分独立组件、与现有社区项目协作的方式开放优化。[^infra-roadmap]

截至 2026 年 10 月，DeepInfer 进一步公开模型执行、并行和调度等引擎能力。官方注明最初主要建立在 vLLM 之上，并借鉴 SGLang、TensorRT-LLM。理解开源史时，应区分论文方法、独立算子库、引擎核心和完整在线服务。[^deepinfer]

### V4.1 的缓存优化与 DeepInfer 的联系

V4.1 的因果编码器—解码器（Causal Encoder-Decoder，CED）结构使解码部分的全局 KV 来自最终编码器状态。CSA2 为层安排 Full、Reindex、Reuse 模式，分别生成全局 KV、重新选择索引，或复用已有 KV 与索引。这些设计减少重复保存与计算。[^v41]

结合 FP4 主 KV 缓存，作者报告全局 KV 约为每词元 890 字节，约为 V4-Flash 对应部分的四分之一。该数字只统计报告定义的全局 KV，不代表模型权重、局部状态、工作区和所有运行内存的总和。[^v41]

SWA Bounded Replay 在缺少局部窗口状态时，仅重放有限长度的近期内容，以减少持久化存储和预填充工作。报告明确说明这种重建是近似的，并用实验评估质量影响。它与数学等价的数据流重排属于不同优化类别。[^v41]

### 判断创新价值的几个维度

| 维度 | 代表工作 | 判断时保留的条件 |
| --- | --- | --- |
| 改变状态表示 | MLA、跨层 KV 共享、CSA2 | 缓存收益需与模型质量、训练和硬件实现一起评估 |
| 改变执行数据流 | FlashAttention、FlashMLA、DeepGEMM | 单算子收益依赖张量形状、硬件和融合上下文 |
| 改变请求组织 | Orca、PagedAttention、SGLang、DistServe | 需比较相同延迟约束、输入输出分布和缓存条件 |
| 减少昂贵生成轮次 | 投机解码、MTP、DSpark、DFlash | 草稿成本、接受长度、验证负载和采样规则共同决定结果 |
| 让稀疏计算可扩展 | DeepEP、EPLB、融合 MoE | 网络拓扑、专家负载和每专家批量会改变瓶颈 |
| 形成可使用的系统 | DeepInfer 等引擎 | 集成与工程价值应单独评价，不能把所有所用思想都归为引擎首创 |

## 优先学习资料

### 选择标准与使用方式

优先材料应围绕明确问题展开，让图、推导或实现承担解释工作，并保留验证条件。较新的发布日期和较高的传播度不直接代表更好的教学质量。大型教材适合查阅，针对单一机制的文章更适合逐篇精读。

下面保留图解、算法、工程和代码四类入口。篇幅较长的文章注明推荐小节；交互页面中的动画和数字主要用于解释机制，不能替代真实硬件测量。

### 注意力变体图解与近期架构

Sebastian Raschka 的《A Visual Guide to Attention Variants in Modern LLMs》（2026-03-22）用一致的图示组织 MHA、GQA、MLA、SWA、DSA 等方法。其教学价值在于让读者比较“共享了哪些头、保存了什么表示、访问了哪些位置”，而非分别记忆缩写。建议先读 GQA、MLA、SWA、DSA 四部分。[^visual-attention]

《Recent Developments in LLM Architectures: KV Sharing, mHC, and Compressed Attention》（2026-05-16）进一步讨论跨层 KV 共享和 DeepSeek-V4。全文较长，优先读第 1 节的跨层共享和第 5.2 节的压缩注意力。它补充了只覆盖 V2/V3 的教程尚未解释的架构变化。[^recent-architectures]

### 用对照实现学习跨层 KV 共享与 DSA

《LLMs-from-scratch》的 `ch04/10_kv-sharing` 保留普通 MHA 与跨层共享两个相似文件，注释也尽量保持一致。直接比较文件差异，可以看清 K/V 的产生层、复用层和缓存管理变化；配套估算脚本将结构变化映射到显存需求。示例模型未经训练，生成内容不用于判断模型质量。[^kv-sharing-code]

`ch04/09_dsa` 展示轻量索引器与 Top-K mask 的关系。它使用稠密注意力计算展示选择逻辑，未实现完整 MLA 或融合稀疏 kernel，因此不能据此声称获得生产系统的稀疏加速。这种明确区分机制展示与性能实现的方式，使它适合作为小型教学代码。[^dsa-code]

### 通过时间线理解批处理

Modular 的《Static, Dynamic and Continuous Batching》提供请求时间线和交互模拟，比较不同批处理方式，并在后半页展示 Whole Prefill 与 Chunked Prefill。建议观察请求何时进入、完成后是否可退出，以及长输入如何暂停其他请求的解码。页面持续更新，未标明确首发日期。[^modular-batching]

图中的行为是简化调度模型。静态批次是否统一等待返回、实际框架如何流式发送结果，取决于实现；连续批处理的关键是可在迭代之间改变执行集合。Modular 的 KV cache offloading 页面还提供缓存容量的补充说明。[^modular-batching][^modular-offloading]

### Mini-SGLang 的中文实现笔记

DarkSharpness 的《mini-sglang》初发于 2025-07-28，更新于 2026-02-12，正文约六千字级别，围绕作者实现过程说明变长批次拼接、张量并行、Attention Backend、CUDA Graph 与 Overlap Scheduler。需要基本 Python 和 PyTorch 阅读能力。[^minisgl-author]

重点推荐 Overlap Scheduler：它将 CPU/GPU 同步、结果回传、下一批准备和流间关系放到同一执行过程中解释。配套阅读 Mini-SGLang 的架构文档，观察 tokenizer、调度器和执行器之间的数据流。官方 2025-12-17 的介绍可以作为项目入口。[^minisgl-structures][^minisgl-release]

这篇属于工程笔记，个别措辞需要校正，例如激活函数并非“大部分是线性的”。它的主要价值是实现思路和同步细节，数学定义应与相应算法或代码核对。[^minisgl-author]

### 无排序采样：一个问题的完整算法推导

FlashInfer 的《Sorting-Free GPU Kernels for LLM Sampling》（2025-03-10）从词表上的排序开销出发，依次介绍逆变换采样、拒绝采样和双支点方法，配有动画、算法步骤、正确性论证及数值实现问题。[^sorting-free]

这篇的优先级较高，因为问题范围集中，读者能跟随作者从朴素实现走到优化方法。阅读时需要区分筛选、采样和完整排序的目标；它也能帮助理解 DeepSelect 一类辅助算子为何值得独立优化。

### 混合模型的统一缓存

《Unified Radix Cache in SGLang》（2026-09-23）用图解释全注意力 KV、滑动窗口状态和递推检查点的不同复用条件，随后介绍统一树、多级存储和会话感知驱逐。建议优先读 Background、Design and mechanism、The safe reuse boundary。[^unified-radix]

它增加的知识是状态复用语义：文本前缀匹配后，还必须验证各组件需要的状态是否齐全。这个问题比“用树保存公共前缀”更接近现代混合模型的部署实际。

### 批次不变性与可复现推理

Horace He 与 Thinking Machines 的《Defeating Nondeterminism in LLM Inference》（2025-09-10）从温度为零仍出现输出变化出发，区分浮点加法顺序、单算子重复执行、不同批次形状和单请求视角的确定性。文中给出小代码例子和相应算子实现。[^determinism]

全文中长，第一遍可读到 Batch invariance and “determinism”；后面的 RMSNorm、矩阵乘法、注意力与实验部分分次阅读。其教学价值在于用可检验的机制替代笼统的“GPU 并行导致随机”解释，与 DeepInfer 的批次不变推理直接相关。

### 六页的 FlashAttention 原理笔记

Zihao Ye 的《From Online Softmax to FlashAttention》（2023-05-11）只有六页，集中解释 softmax 的归一化依赖为何使注意力分块不直接成立，再推导在线统计量与注意力累积。它需要矩阵运算和 softmax 基础。[^online-softmax]

虽然时间较早，这份笔记因主题集中、推导连续而保留为优先材料。理解算法后，再学习线程组织、寄存器和硬件流水线，会更容易区分数学机制与实现策略。

## 学习路线与练习

### 按知识依赖推进

| 阶段 | 主要材料 | 可观察的学习结果 |
| --- | --- | --- |
| 1. 生成过程与瓶颈 | NVIDIA 总览、Horace He、Modular 批处理图解 | 能画出预填充、解码、权重和 KV 的关系，区分算力、带宽与调度开销 |
| 2. 缓存与注意力 | 注意力变体图解、PagedAttention、跨层共享代码 | 能分别计算 GQA、分页、前缀共享和跨层共享省掉了什么 |
| 3. 服务系统 | SGLang 图解、Mini-SGLang、Inside vLLM、Scaling Book 推理章 | 能追踪请求进入、执行、采样、退出，以及缓存分配与回收 |
| 4. DeepSeek | DeepSeekMoE、V2/V3、V3/R1 系统说明、EPLB、DeepEP | 能解释稀疏计算为何需要专家负载均衡与通信配合 |
| 5. 投机与新架构 | 经典投机解码、MTP、DSpark、DFlash、V3.2/V4.1 | 能区分草稿质量、验证开销、稀疏索引与缓存压缩 |
| 6. 底层实现 | 六页在线 softmax 笔记、Triton/CUDA 教程、FlashMLA、FlashAttention-4 | 能把一个具体 kernel 的数据流与硬件瓶颈对应起来 |

阅读最小集合可选：Modular batching、注意力变体图解、跨层 KV 共享对照代码、Mini-SGLang 中文笔记、Sorting-Free Sampling。之后按兴趣选择 Unified Radix Cache、DFlash 2 或 FlashAttention-4。

论文的建议顺序为：MQA/GQA 与 DeepSeek-V2；FlashAttention 与 PagedAttention；Orca、SGLang、DistServe；DeepSeekMoE 与 DeepSeek-V3；经典投机解码与 DSpark。架构、系统和 kernel 三条线交替阅读，避免只熟悉其中一层。

### 小规模练习

1. 用本文公式估算普通注意力的 KV 大小，再改变请求数、上下文长度和 KV 头数。明确哪一项按比例变化，哪些额外开销没有计入。
2. 在批处理图解中追踪长短请求的完成时间，解释更高吞吐为何不一定改善每个用户的延迟。
3. 比较普通 MHA 与跨层 KV 共享文件，标出生成 KV 的层、复用 KV 的层和仍然独立计算的 Q。
4. 在 DSA 教学实现中区分索引打分、Top-K 和最终 mask，说明稠密 mask 实现为什么不自动获得稀疏 kernel 的运算节省。
5. 在小模型引擎中改变批量或输入长度，记录 TTFT、生成速度和总吞吐。实验时固定模型、精度和测量定义，并将编译、热身与稳态执行分开。
6. 阅读一个 kernel 优化案例，为每个改动注明它减少了计算、数据搬运、启动次数还是同步等待；无法对应的加速结论需要进一步查证。

这些是建议练习，本文未执行相应 GPU 实验。运行大模型或多卡案例前，应按具体项目的硬件和版本要求调整规模。

### 常见误读与核对项

| 容易混淆的对象 | 核对方式 |
| --- | --- |
| 完整数学运算与近似策略 | FlashAttention 的重排、稀疏注意力的模型设计、有限重放的近似重建分别判断 |
| KV 表示压缩与分页分配 | 前者改变状态表示，后者改善分配和共享 |
| KV 前缀缓存与语义答案缓存 | 核对缓存对象、匹配条件和是否重新执行模型 |
| 算子加速与端到端加速 | 查看该算子在整个请求耗时中的比例和其他新增开销 |
| 激活参数与总参数 | 低计算量不意味着只需存储激活部分的全部模型状态 |
| 首词元、流式速度与总吞吐 | 查看计算区间、排队时间及延迟约束 |
| 投机解码分布保持与逐字复现 | 查看接受修正规则、随机数路径和批次不变性 |
| 模拟接受长度与真实草稿表现 | 模拟结果不能替代真实任务的接受率和质量评估 |
| 教学代码与生产内核 | 阅读实现明确省略的模型部分、稀疏计算和硬件优化 |
| 旧文章与当前仓库 | 固定代码版本，特别检查硬件、缓存格式和接口变化 |
