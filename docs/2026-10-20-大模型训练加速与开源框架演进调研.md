# 大模型训练加速与开源框架演进调研

更新与资料核对日期：2026 年 10 月 20 日。

本文面向具备基本大模型概念、希望理解训练执行效率的读者。重点是预训练与后训练库如何减少前向、反向、优化器更新和 RL 采样循环中的计算、存储、通信与等待。模型架构和策略优化算法只作为理解工作负载的背景。

研究从开源库的发布记录、代码、测试与性能指南出发，再回溯论文和教学材料。版本节点表示可核实的公开记录，不宣称是相应思想的首次出现。GitHub Release 的发布日期统一换算为北京时间；博客、论文按原站标注日期记录。引用 `main` 的材料只代表核对日期时的状态，具体阅读实现优先使用固定 tag。

验证范围为公开文献、发布记录和静态源码核对，未运行相关 GPU 基准或完整模型训练。项目报告的数值保留其模型、硬件、执行阶段和基线；测试文件的存在只说明项目提供了该验证入口，不代表本文已执行测试。

## 训练与推理优化的对应关系

训练同样包含算子融合、分块计算、动态批次、通信重叠和图执行。它额外需要反向传播、梯度聚合、优化器状态，以及跨阶段存活的中间张量。一个前向更快的实现，只有在反向、数值和状态管理也成立时，才能形成有效训练优化。

| 推理中熟悉的优化                   | 训练中的对应方向                                        | 主要减少什么                          | 代表入口                                                                 |
| ---------------------------------- | ------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------ |
| FlashAttention，避免完整注意力矩阵 | FlashAttention 前向与反向；在线统计量与重计算           | 注意力中间张量和显存读写              | FlashAttention[^flashattention]                                          |
| 只计算最终需要的输出               | 分块／融合 LM head、交叉熵、log-prob、entropy           | 完整 token×词表 logits 及其梯度临时量 | CCE、Liger、TRL[^cce][^liger-paper][^trl-115]                            |
| 变长请求批处理                     | Padding-free、sequence packing、token-budget microbatch | padding 计算和不同 rank 的负载差异    | TRL、verl[^packing-blog][^verl-perf]                                     |
| 前缀复用                           | 同一训练批次内的树形前缀共享                            | 多个样本重复前缀的部分前向计算        | TRL AsyncGRPO tree packing[^trl-116]                                     |
| KV cache 管理                      | 激活保存、选择性重计算、异步 offload                    | 反向所需激活的峰值存活量              | Megatron、TorchTitan[^meg-offload][^titan-graph]                         |
| CUDA Graph 减少启动开销            | 捕获训练步或训练区域、编译前向与反向图                  | CPU launch、图断裂和部分中间操作      | TorchTitan GraphTrainer[^titan-graph]                                    |
| 低精度权重与算子                   | FP8/MXFP8/FP4 GEMM、低精度通信和优化器状态              | 计算、带宽和训练状态容量              | Transformer Engine、TorchAO[^te-primer][^torchao]                        |
| TP/EP 通信重叠                     | AllGather–GEMM、GEMM–ReduceScatter、EP 与反向重叠       | 关键路径上的通信等待                  | FLUX、Triton-distributed、Megatron[^flux-design][^triton-dist][^meg-moe] |
| 减少空闲请求槽位                   | 流水线调度、输入梯度与参数梯度分离                      | pipeline bubble                       | Zero Bubble、DualPipeV[^zero-bubble][^dualpipe]                          |
| 模型装载与缓存复用                 | RL 中 trainer/rollout 显存分时复用、分桶／增量权重同步  | 两种执行阶段切换的停顿和额外副本      | HybridFlow、verl、Miles[^hybridflow][^verl-091][^miles-010]              |

训练中的前缀共享需要在当前参数下建立正确的计算图并汇总反向梯度。跨优化器更新直接复用旧 KV 或旧激活，通常不满足原训练目标的计算要求。不能把推理缓存机制原样移植成训练缓存。

## 一个训练步的执行与内存

### 前向、反向和参数更新

以线性层为例，设输入 $X\in\mathbb{R}^{n\times d}$、权重 $W\in\mathbb{R}^{d\times h}$，输出为 $Y=XW$。若损失对输出的梯度为 $G=\partial L/\partial Y$，则：

$$
Y=XW,\qquad
\frac{\partial L}{\partial X}=GW^\top,\qquad
\frac{\partial L}{\partial W}=X^\top G.
$$

训练因此需要前向矩阵乘法、输入梯度矩阵乘法和参数梯度矩阵乘法。计算参数梯度需要再次使用输入 $X$；计算输入梯度需要权重 $W$。这解释了训练必须保存、重算或重新加载哪些张量，也解释了低精度训练为什么需要分别处理三种 GEMM。[^te-primer]

冻结某层参数后，该层仍可能位于可训练模块的后方。此时可以省略该层的参数梯度，却仍需计算输入梯度，让梯度传回前面的可训练部分。Liger v0.8.4 对冻结 LM head 的优化正是这种依赖裁剪。[^liger-084][^liger-ppo-code]

### 五类主要内存

| 内存对象         | 典型生命周期                   | 常见优化                                        |
| ---------------- | ------------------------------ | ----------------------------------------------- |
| 权重             | 跨训练步存活                   | 参数分片、低精度存储、按层物化                  |
| 梯度与优化器状态 | 跨 microbatch 或训练步         | 分片、延迟同步、融合优化器、状态降精度、offload |
| 激活             | 前向产生，反向消费后释放       | 选择性保存、重计算、CPU offload                 |
| 输出层临时量     | 投影、softmax、loss 和对应反向 | token／词表分块、在线 log-sum-exp、融合接口     |
| 系统缓冲区       | 通信、图执行、预取和阶段切换   | buffer 复用、固定容量分块、控制并发存活量       |

不同方案可能降低其中一项、提高另一项。例如提前 AllGather 需要额外完整参数；异步 offload 需要 pinned memory 和传输中的张量；CUDA Graph 需要稳定地址与图相关内存。优化应比较峰值及其发生阶段，而不仅是某一张量的大小。[^fsdp2][^meg-offload][^verl-perf]

### 输出层的容量例子

假设一个 microbatch 含 8192 个有效 token，隐藏维度为 4096，词表大小为 131072，张量采用每元素 2 字节的表示。隐藏状态与完整 logits 的存储量分别为：

$$
M_{\mathrm{hidden}}=8192\times4096\times2=64\ \mathrm{MiB},
$$

$$
M_{\mathrm{logits}}=8192\times131072\times2=2\ \mathrm{GiB}.
$$

完整 logits 已经是隐藏状态的 32 倍。这个估算尚未包含 FP32 softmax、梯度、中间副本和其他层。因此，小模型配大词表、长上下文时，输出层很容易成为显存热点；减少其物化能使同一设备承载更长序列或更大 microbatch。[^cce][^trl-115]

## 开源库的代表性开发历史

### 调研对象与证据类型

| 层次       | 主要库                                                         | 阅读重点                                            |
| ---------- | -------------------------------------------------------------- | --------------------------------------------------- |
| 训练算子   | Liger-Kernel、CCE、FlashAttention、Transformer Engine、TorchAO | 前向与反向、输出层、精度与临时内存                  |
| 预训练执行 | Megatron Core、TorchTitan、Nanotron、Picotron、Olmo-core       | 并行、激活生命周期、通信、编译与训练 recipe         |
| 后训练执行 | TRL、verl、slime/Miles、AReaL、NeMo RL、Prime-RL               | scorer 热路径、变长数据、rollout/trainer 切换和更新 |
| 配套系统   | Mooncake、DCP、Zephon、NVRx、torchft                           | 传输、数据加载、保存与恢复                          |

发布说明用来定位改动和基准条件；固定版本源码用来核对实际执行；测试用来识别验证覆盖；论文和博客用于解释设计。目录存在、release 宣称支持和某个模型 recipe 已验证是不同强度的证据。

### Liger：从单算子融合到后训练输出层和 MoE 反向

| 公开节点                  | 变化                                                             | 执行层面的含义                                                         |
| ------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 2024 年项目与技术报告     | RMSNorm、RoPE、SwiGLU、CE、Fused Linear CE                       | 融合常见操作，减少中间张量和显存往返[^liger-paper]                     |
| 2024 年末—2025 年         | 后训练 chunked loss；Liger GRPO 接入 TRL                         | 将输出投影与后训练评分结合，按块控制 logits 生命周期[^liger-grpo-blog] |
| v0.8.0，2026-05-01        | `LigerExperts`、grouped GEMM、融合 SwiGLU 与聚合、节省内存的反向 | 减少逐专家 Python/eager 循环和零碎 kernel[^liger-080]                  |
| v0.8.1，2026-07-23        | Megatron 原生集成入口，含词表并行 CE                             | 将优化带入分布式模型，避免只优化单卡 loss[^liger-081]                  |
| v0.8.2—v0.8.3，2026-08—09 | fused scaled CE、TP loss、多后端、logits buffer 复用与反向改进   | 面向 RL 所需 log-prob 与大模型分片调整计算路径[^liger-082][^liger-083] |

v0.8.0 报告的 Qwen3-30B-A3B 大幅加速，针对其给定的两张 H100、长序列微调和原 eager 专家执行基线，不能理解成相对所有成熟 MoE 训练栈都获得同等收益。[^liger-080]

### TRL：从整体 loss 融合转向共享的高效评分接口

| 发布节点                          | 变化                                                                                             | 应保留的边界                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| 2025-05-25 的 Liger GRPO 集成文章 | 分块处理后训练输出和 loss                                                                        | 历史文章的接口和性能条件对应当时实现[^liger-grpo-blog]                                  |
| v1.14.0，2026-09-25               | 将部分训练器从单独重写的 fused loss 迁到共享分块 log-prob 路径；补充融合 log-prob/entropy kernel | loss 公式保持在各训练器中，减少两套实现漂移；仍有不兼容组合[^trl-114]                   |
| v1.15.0，2026-10-09               | 多个训练器改用分块融合 LM head，直接返回 token 级 log-prob/entropy；增加选择性激活 checkpointing | 发布基准区分评分阶段和完整 rollout；既有 chunked SFT 基线并非获得相同容量增益[^trl-115] |
| v1.16.0，2026-10-16               | 实验性 AsyncGRPO 加入前缀树 packing；新增形状对齐与平台修正                                      | 树形共享收益依赖重复前缀；不能推广为所有训练器的默认能力[^trl-116]                      |

这条演进同时包含性能与接口设计：模型内部算子由底层库优化，训练器尽量共享“返回所需评分”的高效入口，再保留各自的 loss 组合。v1.14 的说明记录了重复 loss 实现和分布式包装导致的正确性问题，说明融合范围需要同时考虑梯度同步与维护边界。[^trl-114]

### Miles 与小型训练实验库

Miles v0.1.0（2026-08-18）将异步 RL、低精度、P2P/增量权重传输与优化器状态流式 offload 组织在同一系统中。v0.1.1（2026-09-26）继续降低共置训练峰值内存、优化 NVFP4 路径和状态流式处理；v0.1.2（2026-10-09）加入 TorchTitan 后端及部分模型的反向 kernel 改进。学习时应选择具体模型 recipe，而不是仅凭框架功能总表判断组合可用性。[^miles-010][^miles-011][^miles-012]

Nanochat、Picotron 和 modded-nanogpt 适合观察较小代码库中的完整训练步及优化实验。Picotron 以并行教学为目标；modded-nanogpt 按固定评估目标记录训练速度实验，适合研究优化过程，但其中多项改动和特定硬件基准不能直接外推到大型预训练。[^nanochat][^picotron][^modded-nanogpt]

## 训练热路径的关键优化

### 输出层：不保存完整 logits，也能完成反向

这是最适合从推理优化迁移过来理解的一类技术。设某个 token 的 logits 为 $z\in\mathbb{R}^{V}$，目标 token 为 $y$。交叉熵所需的量为：

$$
\log p_y=z_y-\log Z,\qquad Z=\sum_{j=1}^{V}\exp(z_j).
$$

若还需要熵，则：

$$
H(p)=\log Z-\sum_j p_j z_j.
$$

最终输出只是每个 token 的一个或几个标量。实现可以分块计算词表投影，维护稳定的在线最大值、指数和、目标 logit，以及可选的熵统计量；处理完一块便复用临时空间。反向再重算所需 logits 块，计算输入梯度和权重梯度。这个设计用额外计算换掉大块保存量，与 FlashAttention 的 IO 思路相近。CCE 与 TRL 的具体切块、kernel 和梯度处理不同，不能混称为同一个实现。[^cce][^trl-chunk-code]

TRL v1.15.0 的 `chunked_logprob.py` 是较清楚的阅读入口：矩阵块由 `torch.mm` 计算，Triton kernel 更新统计量，自定义 autograd 组织反向重算和梯度累加。因此，“fused LM head”在这里表示投影与评分被共同调度、避免完整中间量，并不意味着只有一次 CUDA kernel 调用。可结合其 `tests/test_kernels.py` 查看目标值、温度、mask、不同 dtype 和梯度的比较方式。[^trl-chunk-code][^trl-kernel-tests]

分块大小影响显存、GEMM 利用率和启动次数。过小的块可能节省更多内存，却降低算力利用率；词表并行还需要跨 rank 的归一化统计与梯度通信。若某项训练目标确实依赖大量词表分布信息，就需要相应的流式归约实现，不能只保留目标 token 的 log-prob。

Liger v0.8.4 进一步处理冻结输出头：根据 `weight.requires_grad` 决定是否分配并累积权重梯度，仍保留必要的输入梯度。这种按梯度需求裁剪，比笼统地“开启融合 loss”更接近训练执行优化的本质。[^liger-ppo-code]

TRL v1.15 的公开基准使用 B300，并将可用分配器内存限制到约 79 GiB；其 GRPO/RLOO 项固定了生成结果，测量评分训练路径。示例中 GRPO 峰值显存从 24.15 GiB 降到 10.30 GiB，而 tokens/s 约为原来的 1.023 倍。这个结果体现了较大的容量收益和较小的即时吞吐收益，测量范围不含完整在线生成循环。[^trl-115]

### Padding-free 与 packing：减少空 token，并保留训练语义

假设四条序列长度为 4096、1024、512、512，按最长长度补齐共需处理 16384 个 token；去掉 padding 后只剩 6144 个。两者相差约 2.67 倍，这是 token 数的算术比例，不能直接当作实测加速比：注意力复杂度、矩阵形状和通信占比都会影响最终吞吐。

可以区分三个动作：

1. **Padding-free**：保留原来样本分组，展平有效 token，向 varlen attention 提供真实边界。
2. **Packing**：将多个样本装入长度受限的训练序列或批次，改善容量利用；是否允许跨样本注意力取决于训练语义。
3. **Token-budget microbatch**：以有效 token 或计算量限制 microbatch，减少变长样本造成的 OOM 和 rank 等待。

原本独立的样本需要通过 `cu_seqlens` 或等价机制隔离注意力；重置 `position_ids` 本身不能保证所有注意力后端都隔离样本。还需处理 causal label shift、样本边界和 loss mask。2024 年的 Hugging Face packing 文章适合建立机制直觉；实际接口应按当前库版本核对，不能直接复制旧版 collator 配置。[^packing-blog][^packing-paper][^trl-memory]

动态 microbatch 还会影响梯度归一化。如果目标是对全局有效 token 求平均，就应按整个更新所含有效 token 数加权；对长度不同的 microbatch 均值再取平均，会改变目标函数。RL 也可能采用 sequence-level reduction，此时应保留对应的样本权重。verl v0.9.1 修正了 token-budget 分箱的严格上限，表明这些边界属于实际实现问题。[^verl-091][^verl-perf]

### 更少 padding 与更稳定形状需要一起考虑

完全动态的形状可能带来额外编译、autotune、分配和图捕获。长度分桶让相近样本进入同一组，再适当补齐到少量形状，可以提高缓存和图重放命中率。应比较“多算一点 padding”与“少编译、少启动、少分配”的总成本。

verl v0.9.0 的形状分桶和 TRL v1.16 的 Trainium 对齐控制都体现了这个问题，但不同硬件和后端的编译成本不能互相套用。记录 shape 数量、重编译次数与冷启动时间，才能解释为什么某个 padding 更少的配置反而更慢。[^verl-090][^trl-116]

### 训练中的前缀共享：树形批次与梯度汇总

RL 中，同一个 prompt 常产生多条 completion；多轮 agent 轨迹也会共享很长的历史。若每条样本完整重算前缀，线性层、归一化和注意力的一部分工作会重复。

TRL v1.16.0 的实验性 AsyncGRPO tree packing 将共享路径表示成树，压缩没有分叉的链为 segment。独立 token 的非注意力计算可以共享；注意力通过为每个 segment 收集祖先路径上的 K/V，并调用 varlen attention 实现。共享路径的 K/V 在这种组织中仍可能重复参与收集和注意力，不能理解为全部计算都只做一次。[^trl-tree-code]

反向需要把各分支对共享前缀的贡献相加，评分还需映射回原始样本及其 loss 权重。阅读该实现时，值得跟踪 `tree_kv_index`、query/key 的累计长度，以及“样本 token 数”和“实际前向 token 数”的区别。发布基准显示收益依赖前缀共享程度，无共享时没有稳定收益。该路径也不是通用 SFT/GRPO 默认配置。[^trl-116][^trl-tree-code]

### 激活管理：保存、重算与搬运是三个可组合的选择

反向只要求在需要某个张量时拿得到它，并不要求一直把它保存在 GPU。可以按张量选择：

| 策略        | 付出的成本                    | 更适合的情况                                 |
| ----------- | ----------------------------- | -------------------------------------------- |
| 保留        | GPU 存储和存活时间            | 重算贵、张量不大，或复用频繁                 |
| 重计算      | 额外前向 FLOPs 和可能重复通信 | 操作便宜、输出大，例如部分激活和归一化中间量 |
| CPU offload | D2H/H2D、主机内存、同步管理   | 张量大、重算贵，并且有可隐藏传输的时间窗口   |

整层 checkpoint 易于使用，但会重新运行其中所有被包住的计算。选择性 checkpoint 可以保留昂贵 GEMM 或注意力的结果，重算较便宜部分。PyTorch 的官方图解明确比较了普通 checkpoint、selective checkpoint 与编译器内存策略，是入门这一权衡的优质短文。[^activation-blog]

Megatron 的细粒度 offload 文档进一步讨论层内子模块的输入：前向异步卸载，反向前预取，并限制在途张量。流水线不同 stage 同时保留的 microbatch 数量不同，offload 策略因此应考虑 stage 位置。其成本不是简单的“PCIe 带宽够不够”，还取决于能否在消费之前完成预取，以及传输和其他通信是否争用资源。[^meg-offload]

FSDP 与 checkpoint 的组合也要查看时间线：重算可能重新触发参数 AllGather；过早预取会抬高显存峰值。局部算子的重算成本很低，不代表放进完整分布式训练后仍然便宜。[^fsdp2][^titan-fsdp]

### 编译与 CUDA Graph：覆盖前向之外的训练阶段

`torch.compile` 可以优化图中的算子组合与调度；CUDA Graph 主要减少重复执行时的 CPU launch 开销。两者可以配合，但不是同一件事。训练还涉及反向、优化器更新、通信和 RNG，因此比只捕获一次固定形状前向更复杂。

TorchTitan GraphTrainer 将前向、loss 与反向放入共同分析范围，并提供图级内存策略；GraphPP 进一步探索跨流水线的执行。这里最值得学习的是：编译器能在更大的依赖图上判断哪些张量需要保留、何时重算、哪些工作可以调度在一起。[^titan-graph]

图执行尤其适合稳定形状、重复运行且 launch 开销明显的区域。动态 MoE 路由、变长样本、分配和某些通信路径会限制捕获范围，因此 Megatron 同时提供区域级图捕获。衡量收益时应分开报告首次编译／捕获、稳定训练步和图相关显存，不能只报告排除所有准备成本后的最佳迭代。[^meg-moe][^titan-graph]

### 优化器更新：融合逐元素操作，减少启动与读写

AdamW 更新会读取梯度、参数及一阶／二阶统计量，并写回更新结果。如果逐参数、逐操作执行，会产生许多小 kernel 和中间张量。横向融合将多个参数张量的同类操作一起处理；纵向融合将同一参数上的连续操作合并，减少中间读写。PyTorch 的 AdamW 文档区分了单张量循环、`foreach` 和 `fused` 路径，也说明 `foreach` 的临时 tensor list 会增加峰值内存。[^adamw-doc]

另一个入口是编译 optimizer step。PyTorch 官方教程用小模型单独测量这一阶段，适合研究计算图与 launch 开销；它的结果只代表优化器更新。配套学习率调度教程还展示了一个容易忽略的细节：在其示例中，变化的 Python 标量学习率触发重编译，使用受支持的 tensor 学习率可避免该问题。实际配置仍需匹配优化器实现与图捕获条件。[^compile-optimizer][^compile-scheduler]

### 长上下文：切分序列，并重新安排注意力数据

FlashAttention 减少注意力中间量的存储，但精确密集注意力的计算仍随长度呈二次增长。单个长样本放不下时，仅增加数据并行卡数不能缩小该样本在每卡上的激活，需要沿序列维度切分。

Ulysses 将各卡持有的序列片段，通过 all-to-all 转换为“完整序列的一部分 attention heads”，完成注意力后再换回原布局。它用通信换取每卡更少的激活与注意力工作，并对 head 数、切分和 label shift 提出要求。2026 年的 Hugging Face 教程包含这些机制及训练集成，适合与固定长度的数据并行基线对照。[^ulysses-paper][^ulysses-blog]

变长训练还可以按样本长度调整上下文并行度，让短样本避免不必要通信，让长样本使用更多卡。verl v0.9.0 的动态 CP 是相关实现入口。比较时需同时看每 rank 的有效工作和 collective 等待，序列均分并不自动等于计算均衡。[^verl-090]

### 低精度：训练要处理三种 GEMM 和持久状态

推理低精度主要关注权重、前向激活和缓存。训练还需处理激活梯度、参数梯度、优化器累积量及更新数值。前向可用的缩放方式，不一定适合梯度分布；不同 GEMM 的矩阵布局和转置还会影响数据转换成本。

Transformer Engine 的 FP8 primer 从格式、缩放与数值范围解释这些问题；TorchAO 提供 PyTorch 侧的低精度训练与实验路径。阅读 MXFP8、NVFP4 时，应同时查看硬件要求、scale 粒度、参与的操作，以及哪些计算继续保留较高精度。[^te-primer][^torchao]

2026 年 TorchTitan 的 MXFP8＋DeepEP 文章展示了低精度计算与专家通信的组合优化。其 671B 模型吞吐实验与较小模型的短程 loss 对比属于不同证据：前者说明特定集群上的性能，后者支持有限范围内的数值检查，不能合并成“671B 完整训练收敛已证实”。[^titan-mxfp8]

优化器状态也可以单独降精度。TorchTitan v0.3.0 的 BF16 状态说明值得与其实现一起读：减少的是持久状态内存，代价与更新精度及补偿方式相关。常见的“每参数固定 16 字节”估算只适用于特定存储组合，不能覆盖所有优化器和分片方案。[^titan-bf16]

### MoE：Grouped GEMM 之后，重排与反向仍有大量空间

MoE 把 token 路由到不同专家。逐专家 Python 循环和小 GEMM 会带来启动开销与较差利用率，Grouped GEMM 可以共同调度这些矩阵。但路由、permutation、激活保存、专家输出汇总和 EP 通信仍会消耗时间与显存。

SonicMoE 将重点放在 IO、tile 利用率和反向激活保存；Liger v0.8.0 的专家实现把 grouped GEMM、SwiGLU 与汇总组织到同一 autograd 路径。Megatron 的版本记录还包含将路由概率乘法移入专家计算、减少重排临时量等更细的变化。它们比“采用 MoE 所以更高效”提供了更具体的优化对象。[^sonicmoe][^liger-080][^meg-moe]

DeepEP 负责高效专家 dispatch/combine；DeepGEMM 提供低精度矩阵计算基础。将两者组合时，通信 kernel 可能占用 SM、缓冲区和网络资源，与计算竞争。最优配置通常与专家粒度、每专家 token 数、节点间带宽有关。低延迟推理 dispatch 的配置，也不能直接代表大吞吐训练的最佳配置。[^deepep][^deepgemm]

### 通信与计算融合：让数据分块到达，分块消费

粗粒度调度经常是“完整 AllGather → 完整 GEMM”或“完整 GEMM → ReduceScatter”。它们之间存在大块等待。更细粒度的实现让一部分输入到达后立即开始对应计算，或让一部分输出完成后立即启动归约。

FLUX 的设计文档用 AllGather–GEMM 与 GEMM–ReduceScatter 解释这种依赖关系，篇幅短，适合先读。Triton-distributed 则提供可以继续追到实现和端到端示例的入口。其示例也说明，某些小矩阵采用 GEMM＋AllReduce 可能更合适：分块同步和融合本身有成本。[^flux-design][^flux-paper][^triton-dist][^triton-dense]

这类优化与“在另一条 CUDA stream 上发通信”有区别：真正的收益取决于数据块的生产和消费依赖、SM 占用、内存访问和同步粒度。2026 年的 GPU-initiated communication 研究及其小型实验代码，适合进一步理解由 GPU 直接推进通信的机制。[^gpu-comms]

### FSDP 的预取、通信桶与梯度累积

FSDP 的主要步骤包括需要时汇集参数、执行层计算，以及归约／分片梯度。调整分片单元与通信桶大小，会改变启动次数、可重叠窗口及峰值内存。过细会增加通信和调度成本；过粗会降低重叠机会，且需要同时保留更多完整参数。FSDP2 教程适合把这些机制与模块边界对应起来。[^fsdp2]

梯度累积期间延迟同步可以减少通信次数，但可能让更多未分片梯度存活。因此，`no_sync` 或类似控制并非无条件节省内存的开关。TorchTitan 的 FSDP 说明和 verl 的性能指南都适合结合 profiler 检查这一权衡。[^titan-fsdp][^verl-perf]

SimpleFSDP 则把部分分片管理表达成编译器可以理解的形式，适合在掌握 FSDP2 后研究通信调度与编译的交点。[^simplefsdp]

### 流水线：输入梯度在关键路径上，参数梯度可以晚一点

传统叙述把 backward 当作一个整体。实际上，某 stage 的输入梯度必须尽快返回上一个 stage；该 stage 的参数梯度通常只需在参数更新前完成。因此可将 backward 拆成输入梯度部分和参数梯度部分，把后者安排到原来的空闲窗口。

Zero Bubble 研究了这种调度空间；DualPipe/DualPipeV 将流水线、通信重叠和实际模型执行结合起来。收益来自依赖重排，不是删除了参数梯度计算。它可能延长激活存活、需要更多缓冲区，也需要明确梯度归约和优化器更新的同步位置。[^zero-bubble][^dualpipe]

DualPipe 仓库提供调度参考，但真正把计算与通信重叠起来，需要模型端实现对应的细分执行接口。只移植调度器，不拆开层内计算，未必得到论文中的重叠效果。

## 后训练与 RL 的执行优化

### 从一次 RL 迭代看瓶颈

一轮常见的在线 RL 包括 prompt 装载、rollout、环境或 reward、策略／参考模型评分、actor 更新，以及将新权重交给下一轮 rollout。某些算法没有独立 critic，固定参考模型也可能提前评分；实际阶段应按所用目标与实现画出。

同步系统的迭代时间可近似理解为这些阶段的总和；异步系统的稳定吞吐更多受最慢生产／消费阶段、队列和背压约束。将两个阶段重叠并不消除总工作，还会引入样本版本和参数版本的距离。HybridFlow、AReaL 和 Miles 分别适合研究角色组织、异步执行和近期训练／生成集成。[^hybridflow][^areal-paper][^miles-010]

| 阶段           | 典型浪费                                    | 优化入口                              | 要保留的语义                       |
| -------------- | ------------------------------------------- | ------------------------------------- | ---------------------------------- |
| Rollout        | 长尾请求阻塞、重复 prefill、KV 容量不足     | 连续批次、前缀复用、异步采样          | 实际采样 token、行为策略概率与版本 |
| 评分           | 完整 logits、重复 prompt、无用 entropy 计算 | 分块 LM head、padding-free、树形批次  | 温度、mask、归一化与每个样本的权重 |
| Actor update   | 激活峰值、过多梯度同步、rank 长度不均       | 选择性重算、动态 microbatch、延迟同步 | 全局梯度缩放及更新次数             |
| 阶段切换       | 重复参数副本、优化器和 KV 同时占满显存      | 分时复用、异步 offload、缓冲区复用    | 内存所有权与使用完成时刻           |
| 权重发布       | 完整导出、CPU 中转、大量小传输              | 分桶、分片／增量、设备间传输          | rollout 看到完整一致的参数版本     |
| 环境与轨迹传输 | CPU 序列化、进程搬运、慢环境                | 数据面分离、队列、异步环境 worker     | 完整轨迹与可恢复状态               |

### 评分路径：只计算目标需要的量

对已经生成的序列进行策略更新时，常需动作 token 的 log-prob、可选 entropy，以及与参考策略有关的项。可以先优化这些基础评分输出，再由训练器组合 PPO、GRPO 或其他目标。这样能复用分块输出层，同时减少为每种 loss 复制一份 kernel 逻辑的维护成本。TRL v1.14—v1.15 的变化正好展示了这个接口演进。[^trl-114][^trl-115]

verl 的固定版本中，`linear_cross_entropy.py` 是观察自定义 autograd 返回 log-prob 与 entropy 的简短入口；对应测试可帮助理解其前后向契约。Liger 的 `grpo_loss.py` 展示另一种将评分与目标计算共同组织的路径。两者适合并排阅读，比较融合范围、临时量和可扩展性。[^verl-linear][^verl-linear-tests][^liger-grpo-code]

固定 reference model 对固定训练样本的结果可以预计算或缓存；当前 actor 更新后的评分一般必须重算。rollout 时的 old log-prob 则需要保留实际行为策略的信息，不能用更新后的 actor 无条件替换。温度、tokenizer、精度和采样器差异会让“同一组权重”也产生不同概率，TITO 与训练／推理差异的资料适合解释这些接口条件。[^tito][^rollout-correction]

### 显存复用：训练状态与 KV cache 争用同一设备

共置模式下，rollout 想把内存留给 KV 和生成图；训练想把内存留给梯度、激活和优化器状态。在时间上不重叠的两阶段，可以释放或卸载暂时不用的对象，并在切换时重新加载。分离模式减少同卡争用，但需要专用资源和跨角色数据／权重传输。

值得跟踪的是每次切换的峰值：旧对象是否已经释放，传输是否还持有引用，图内存池是否保留，接收方是否又分配了一份完整权重。verl v0.9.1 中的 offload、IPC 生命周期修正和可选空闲 GPU 借用，比单一的“显存利用率设为多少”更能说明系统如何运行。[^verl-091]

Miles 的近期版本还涉及 CPU/NVMe 上的优化器状态流式处理。它扩展了可容纳的训练状态，但传输如果暴露在关键路径上仍会降低吞吐。应分别记录训练阶段、生成阶段和切换瞬间的内存，而不是只测模型加载完成后的占用。[^miles-010][^miles-011]

### 权重更新：传什么、如何分块、何时可见

训练后端可能使用 TP、EP、PP 或 FSDP 分片，rollout 后端使用另一种布局。朴素方案先还原完整参数、转换格式、经 CPU 中转后广播，会带来多份副本和较长停顿。

更高效的路径包括按固定容量分桶、直接传递可复用分片、边转换边发送，以及使用增量信息减少传输。增量同步需要基线版本一致；量化权重还涉及 scale 与布局更新。参数发送完成、接收完成和推理端可以安全使用新版本，也应是明确的事件。LMSYS 2026 年的 P2P 更新文章和 verl 的分片同步记录适合作为实现入口。[^p2p-blog][^verl-090][^verl-091]

权重传输与轨迹传输解决不同问题。Miles/Mooncake 的 rollout data transfer 文章关注生成结果等数据的传递，不应把其中的吞吐数据直接称为参数同步速度。[^mooncake-rollout]

### 异步 RL：优化队列，同时约束陈旧度

异步执行能减少 trainer 等 rollout、rollout 等 trainer 的空闲，但样本可能来自较旧权重。系统需要记录策略版本、限制队列积压，并明确接受哪些样本。异步系统的评价因此至少包含吞吐、样本陈旧度分布、丢弃率，以及达到同等效果所用的墙钟时间。AReaL 的论文与实现适合深入这一层。[^areal-paper][^areal]

Agent RL 还要考虑环境调用、工具延迟和轨迹长度分布。Prime-RL、OpenEnv、NeMo Gym 等项目值得关注，但它们的环境和工作流能力应与 GPU 算子性能分开评估。只提高环境并发、却让 trainer 队列积压，未必提高有效训练速度。[^prime-rl][^openenv][^nemo-gym]

### 数据加载也必须参与恢复

训练参数恢复了，不代表训练过程已恢复：数据游标、随机状态、打包状态和并行度变化都可能导致重复或跳过样本。Zephon 的 TorchTitan 集成文章发表于 2026-10-16，重点是弹性情况下的数据加载确定性，适合与数据状态保存一起学习。其论文、仓库和集成文章提供了从问题到实现的完整入口。[^zephon-blog][^zephon-paper][^zephon-repo]

### 异步 checkpoint：减少停训时间，而非只提高写盘带宽

异步保存通常先把训练状态暂存到可安全访问的位置，再由后台写入。关键在于主训练线程何时可以继续，以及下次保存是否撞上未完成的后台任务。PyTorch 的异步 checkpoint 文章讨论了后台处理、进程与规划开销；标题中的加速比例对应其 checkpoint 场景，不能当作完整训练速度提升。[^dcp-blog][^dcp-recipe]

保存频率、额外内存和恢复代价应共同权衡。对于大集群，正常训练步之外的故障发现、重启、重新加载和数据恢复时间，会影响整个作业的有效产出。NVRx 与 torchft 分别提供可继续研究的恢复与容错实现。[^nvrx][^torchft]

### 稳态性能之外的测量

Smol Playbook 的运行经验、Olmo-core 的扩展文章和 AWS 的分布式训练实践可帮助建立排查顺序：先分清数据饥饿、CPU 开销、计算、内存和通信，再使用针对性工具。`nvbandwidth`、`nccl-tests` 和 DCGM 用于硬件／通信基线；Flight Recorder 用于分布式 hang 的线索收集。它们解释异常，不代替模型训练基准。[^smol][^olmocore-blog][^aws-distributed][^diagnostics][^flight-recorder]

### 一条可执行的学习路线

1. **先完整理解一次训练步。** 用 Nanochat 或 Picotron 对照前向、反向、更新，列出权重、激活、梯度和优化器状态。此时先不堆多种并行。
2. **选择一个可独立解释的热点。** 首选大词表输出层，读 CCE 介绍和 TRL 分块代码；能解释为什么节省内存、为什么需要重算，就进入下一步。
3. **加入变长数据。** 对比 padded、padding-free 和 token-budget microbatch，核对边界与梯度归一化，而后观察吞吐。
4. **理解显存与通信的交换。** 阅读 FSDP2、选择性 checkpoint 和 Megatron offload，画出张量产生、卸载、预取、消费的时刻。
5. **进入通信融合和 MoE。** 从 FLUX 两个核心图开始，再看 Triton-distributed、DeepEP 与 SonicMoE，解释资源竞争及适用形状。
6. **最后扩展到在线 RL。** 选 TRL 理解 scorer，再选 verl 或 Miles 追完整循环；分阶段记录时间与内存，并追踪样本和权重版本。

这条路线中的实验是建议，本文没有执行。单卡先研究输出层、packing、checkpoint 和编译；多卡再研究 FSDP 与通信。需要集群规模才能体现的流水线和专家通信，可先读小示例及固定条件的项目基准。

## 测量与正确性检查

### 性能记录应当包含什么

| 维度       | 最少记录项                                               | 常见误读                                    |
| ---------- | -------------------------------------------------------- | ------------------------------------------- |
| 实验对象   | commit/tag、模型、参数量、词表、上下文长度与长度分布     | 把小词表结果外推到大词表，或反过来          |
| 硬件与软件 | GPU 型号与数量、互联、驱动、框架、kernel 版本            | 将限制显存的 B300 标为 H100                 |
| 训练预算   | global batch、microbatch、累积步数、有效 token、更新次数 | 批次语义变化后仍声称只改执行                |
| 吞吐       | 有效 token/s、forward token/s、step time、每阶段时间     | 将 padding token 或重复前缀算作有效训练产出 |
| 内存       | allocated/reserved、峰值时刻、CPU pinned/NVMe 占用       | 只报告模型常驻内存，漏掉切换和临时量        |
| 编译与图   | 首次编译／捕获、重编译、稳定步与总墙钟时间               | 只报告预热后的最好一次                      |
| RL 特有项  | rollout 长尾、队列、陈旧度、权重同步、环境时间           | 将 actor update 加速当成完整 RL 加速        |
| 最终效果   | 同等质量所需时间／GPU 小时、失败和恢复损失               | 更快跑完一个 step，却需要更多 step          |

如果一次迭代中某热点占比为 $f$，将该热点加速 $s$ 倍，而其他部分不变，则总加速约为：

$$
S=\frac{1}{(1-f)+f/s}.
$$

例如，评分原本只占迭代时间的 20%，即使其速度翻倍，总加速也只有约 1.11 倍。异步系统还需用实际关键路径和阶段吞吐分析，不能机械相加各项局部加速比。

### 等价执行优化需要核对哪些量

一次合理的验证应逐级扩大：先比较小张量前向与所有需要的梯度，再比较单步参数更新，然后检查分布式缩放与短程 loss，最后测端到端质量和时间。低精度方案允许特定数值误差，但应明确误差基线及收敛证据。

| 优化                  | 重点核对                                                           |
| --------------------- | ------------------------------------------------------------------ |
| Chunked／fused 输出层 | 目标 log-prob、entropy、输入／权重／bias 梯度、忽略 token 和温度   |
| Packing／tree packing | attention 边界、label shift、样本计数、共享前缀梯度累计            |
| 动态 microbatch       | token 或 sequence reduction 是否保持原目标，跨 rank 的权重是否一致 |
| Checkpoint／offload   | RNG 与 dropout、一致的重计算、传输完成和张量存活                   |
| FSDP／延迟同步        | 梯度归约次数、平均因子、更新时刻和内存峰值                         |
| 低精度                | scale、溢出、梯度和优化器状态误差；足够长的质量比较                |
| RL 异步／权重同步     | 行为策略版本、概率来源、整套权重可见性、丢弃与陈旧度               |

TRL 的 kernel 测试、verl 的评分测试和各项目的 recipe 是验证入口。本文核对了这些代码及公开记录，但没有运行它们，也没有将项目声称的测试覆盖视为本文复现实验。[^trl-kernel-tests][^verl-linear-tests]

## 训练阶段与算法背景

这些概念用于解释基础设施的工作负载；算法演进不作为本篇主线。

| 阶段                    | 目标与典型工作负载                                   | 对执行优化的影响                                          | 背景材料                                                                  |
| ----------------------- | ---------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------- |
| Pretraining             | 大规模 next-token prediction，通常具有较稳定的数据流 | 关注长期稳定吞吐、扩展效率、数据恢复和单位有效 token 成本 | Chinchilla、Smol Playbook[^chinchilla][^smol]                             |
| SFT                     | 在指令、对话或其他目标样本上监督学习                 | 变长样本、loss mask、大词表输出层和较小 microbatch 更常见 | TRL、packing 教程[^trl-memory][^packing-blog]                             |
| Preference optimization | 对 chosen/rejected 等偏好数据优化                    | 成对样本、reference 评分及缓存、重复前缀                  | DPO[^dpo]                                                                 |
| 在线 RL                 | 生成新样本、奖励或环境反馈、策略更新                 | 需要调度生成与训练，处理长尾、版本和权重切换              | InstructGPT、DeepSeekMath、DeepSeek-R1[^instructgpt][^deepseek-math][^r1] |

模型规模、训练 token 数与质量的配比决定“要做多少训练”；本篇讨论的执行优化决定“这些训练如何高效完成”。同样，PPO/GRPO 等目标决定需要哪些概率、奖励和梯度，而后训练系统负责尽量少物化、少搬运、少等待地计算它们。评价任何改动时，先说明它是否保持训练目标和预算，再讨论速度。
